# Aithena v2.5.0 Release Notes — Solr 10 Upgrade

_Date:_ 2026-06-06
_Prepared by:_ Newt (Product Manager)

## Summary

Aithena v2.5.0 is a major infrastructure release centered on the **Solr 10 upgrade**. Solr 10 is now the default runtime, replacing Solr 9 across all deployment topologies. This release delivers the complete Solr 9→10 migration: updated schema parameters, rewritten CLI tooling, hardened security posture (including Solr 10's new `blockUnknown` default), a simplified Security UI page in the admin portal, and comprehensive E2E test coverage for the new engine. A Solr 9 rollback overlay is preserved for operators who need a temporary fallback.

### Highlights

1. **Solr 10 as default runtime (#1680)** — `solr:10` is now the default base image. Tika is added as a dedicated document-processing service. A Solr 9 rollback overlay (`docker/compose.solr9.yml`) is available.
2. **HNSW schema migration (#1667)** — Solr 10 HNSW parameter names (`hnswM`, `hnswEfConstruction`) are now used throughout the configset. A compatibility shim handles Solr 9 schema format during the transition window.
3. **solr-init CLI rewrite (#1673)** — All `solr-init` scripts updated to Solr 10 double-dash CLI syntax (`--zk-host`, `--solr-url`, etc.).
4. **`blockUnknown` security hardening (#1663)** — Solr 10 defaults `blockUnknown=true`; health checks and admin tooling now authenticate correctly against secured endpoints.
5. **Simplified Security UI (#1674, #1677)** — New **Admin → Security** page links operators directly to Solr 10's built-in Security UI for day-to-day user and role management.
6. **Solr Security UI backend hardening (#1675, #1681)** — Admin infrastructure URL handling is hardened; nginx access controls for the Security UI are tightened.
7. **E2E test coverage for Solr 10 (#1676, #1679)** — Preflight and runtime E2E tests validate the Solr 10 migration path in CI.
8. **OpenVINO release gate hardening (#1666, #1668)** — Smoke tests for `embeddings-server-openvino` now capture full failure diagnostics; OpenVINO version constraints are locked to the base image.
9. **`wt=json` enforcement (#1664)** — All `solr-search` query paths now explicitly request JSON responses from Solr, locking the search response schema for Solr 10 compatibility.
10. **PathHierarchyTokenizer verified (#1665)** — Folder-path facet tokenization confirmed compatible with Solr 10 with no changes required.

## Breaking Changes

### Full Solr Reindex Required

**Upgrading from v2.3.0 to v2.5.0 requires a full Solr reindex.** The HNSW dense-vector field parameter names changed between Solr 9 and Solr 10 (`hnswMaxConnections`→`hnswM`, `hnswBeamWidth`→`hnswEfConstruction`). Existing collections indexed under Solr 9 cannot be read by Solr 10 without re-bootstrapping.

See [Upgrade Instructions](#upgrade-instructions) and the [Solr 10 Production Migration Runbook](../migration/solr-10-production-runbook.md) for the full procedure.

**Estimated downtime:** 2–8 hours depending on collection size. Plan a maintenance window.

### `VECTOR_QUANTIZATION=int8` Temporarily Unsupported

The `int8` scalar quantization mode (`VECTOR_QUANTIZATION=int8`) is **not supported in v2.5.0**. A low-level Solr 10 quantization bits incompatibility is under review (PR #1670 on hold). Deployments currently using `int8` must switch to `none` (default float32) before upgrading.

Supported `VECTOR_QUANTIZATION` values in v2.5.0: `none` (default), `fp16`.

`int8` will be re-enabled in a v2.5.1 patch once the quantization fix is validated.

### Tika Service Added

`tika` is now a dedicated service in the Docker Compose stack. Operators using custom Compose overrides must ensure the new service is included. The standard `docker-compose.yml` includes it automatically; only custom `COMPOSE_FILE` chains may need updating.

### Solr 10 Java 21 Requirement

The Solr 10 base image requires Java 21. This is bundled in the container image; host-level Java is not required. Operators running the Solr image in custom runtimes (outside the provided Compose stack) must ensure Java 21 is available.

## Operator Responsibilities (v2.5.0)

### Security UI Admin Workflow

Solr 10 includes a built-in Security UI accessible at `/admin/solr/ui/#/~security`. Aithena's admin portal now provides a direct link from **Admin → Security**.

**Important**: Aithena application users (managed in **Admin → User Management**) and Solr users/roles (managed in the Solr Security UI) are separate systems. Do not confuse them:

- Aithena users control access to the Aithena application and proxied admin surfaces.
- Solr users/roles control direct Solr API and UI permissions.
- Use a Solr account with `security-edit` permission for state-changing Solr security operations.

See the [Admin Manual — Solr 10 Security UI](../admin-manual.md#solr-10-security-ui-v25) section for full guidance.

### Solr 9 Rollback Overlay

A Solr 9 rollback overlay is available at `docker/compose.solr9.yml` for operators who cannot immediately complete the reindex. To use it:

```bash
docker compose -f docker-compose.yml -f docker/compose.solr9.yml up -d
```

The rollback overlay is provided as a temporary fallback only. It will be removed in a future release. Operators should plan to complete the Solr 10 migration.

### `blockUnknown=true` in Solr 10

Solr 10 defaults `blockUnknown=true` in its security configuration, meaning all unauthenticated requests to the Solr API are rejected by default. Aithena's health checks, `solr-init`, and CI validation have been updated to authenticate correctly. Operators with custom scripts that probe Solr without credentials should update them to use the admin credentials from `.env`.

## Upgrade Instructions

> **Read the full [Solr 10 Production Migration Runbook](../migration/solr-10-production-runbook.md) before starting.** The runbook covers pre-migration checklist, phased cutover procedure, validation, rollback, and troubleshooting.

### Summary: From v2.3.0 → v2.5.0

1. **Verify prerequisites:**
   - Docker v20.10+
   - Docker Compose v2.0+
   - Host `vm.overcommit_memory=1` (required since v2.3.0)
   - If using `VECTOR_QUANTIZATION=int8`: change to `none` or `fp16` before proceeding.

2. **Back up your data** (required before reindex):
   ```bash
   # Trigger a manual Solr backup via the admin portal
   # Admin → Backups → Backup Now
   # or use the backup script
   bash scripts/backup.sh
   ```

3. **Pull the latest images:**
   ```bash
   docker compose pull
   ```

4. **Stop the stack:**
   ```bash
   docker compose down
   ```

5. **Restart with Solr 10 (default):**
   ```bash
   docker compose up -d
   # or: ./start.sh
   ```

   To use the Solr 9 rollback overlay temporarily:
   ```bash
   docker compose -f docker-compose.yml -f docker/compose.solr9.yml up -d
   ```

6. **Wait for all services to stabilize** (60–90 seconds). Monitor `solr-init`:
   ```bash
   docker compose logs -f solr-init
   ```

7. **Trigger a full reindex:**
   ```bash
   # Admin portal → Reindex Library → Reindex All
   # or via API:
   curl -sf -X POST http://localhost/v1/admin/reindex -H "Cookie: aithena_auth=<token>"
   ```

8. **Verify services:**
   ```bash
   curl -sf http://localhost/v1/health | jq .
   curl -sf http://localhost/admin && echo "✅ Admin portal accessible"
   curl -sf http://localhost/v1/capabilities | jq .
   ```

9. **Validate Solr 10 posture:**
   ```bash
   # Solr version
   curl -s -u "$SOLR_ADMIN_USER:$SOLR_ADMIN_PASS" http://localhost:8983/solr/admin/info/system | jq .lucene.solr-spec-version

   # Collection health
   curl -s -u "$SOLR_ADMIN_USER:$SOLR_ADMIN_PASS" http://localhost:8983/solr/admin/collections?action=CLUSTERSTATUS | jq '.cluster.collections.books.health'
   ```

### For Fresh Installations

```bash
# 1. Apply host prerequisites
sudo sysctl vm.overcommit_memory=1
echo "vm.overcommit_memory = 1" | sudo tee /etc/sysctl.d/90-redis-overcommit.conf

# 2. Run the installer
python3 -m installer

# 3. Start the stack
./start.sh

# 4. Wait for services to stabilize (60–90 seconds)
sleep 90

# 5. Run health checks
curl -sf http://localhost/v1/health | jq .

# 6. Verify Solr 10 is running
curl -sf http://localhost/admin && echo "✅ Admin portal accessible"
```

## Validation Steps

### Post-Upgrade Validation

```bash
# 1. Host sysctl is applied
cat /proc/sys/vm/overcommit_memory
# Expected: 1

# 2. Service health
curl -sf http://localhost/v1/health | jq .

# 3. Search works
curl -sf "http://localhost/v1/search?q=test&mode=keyword" | jq .total

# 4. Solr 10 version confirmed
docker compose exec solr /opt/solr/bin/solr version

# 5. ZooKeeper ports are not exposed on host
netstat -tuln | grep -E "(2181|2888|3888)" || echo "✅ ZooKeeper ports private"

# 6. Container logs clean (no unallowlisted errors)
docker compose logs | grep -i "ERROR" | head -10
```

### Pre-Release Check (CI)

The CI validation workflow checks:

- ✅ Solr 10 image builds successfully
- ✅ `solr-init` bootstraps collection with Solr 10 CLI syntax
- ✅ Collection health is GREEN after bootstrap
- ✅ `blockUnknown=true` health checks authenticate correctly
- ✅ HNSW dense-vector fields index and query successfully
- ✅ Search API (keyword, semantic, hybrid) returns results
- ✅ Admin portal is accessible
- ✅ E2E Playwright tests pass
- ✅ Compose security regression (ZooKeeper ports private, Solr auth vars present)

## Known Issues & Limitations

- **`VECTOR_QUANTIZATION=int8` disabled** — Scalar quantization with Solr 10's int8 codec is temporarily unavailable due to a quantization bits incompatibility (PR #1670 on hold). This will be re-enabled in v2.5.1. Use `VECTOR_QUANTIZATION=none` (default float32) or `VECTOR_QUANTIZATION=fp16`.
- **cuVS GPU-accelerated indexing deferred** — GPU codec support for Solr (`cuVS`) is not included in v2.5. Planned for v2.5.1+ with a separate NVIDIA-enabled Solr image.
- **`language-models` embeddings module deferred** — Making `embeddings-server` optional via Solr's native `language-models` module depends on upstream LangChain4j work; deferred to v2.6.
- **RabbitMQ 4.x deprecation warnings** — Allowlisted since v2.3.0. These are informational and do not indicate functional problems.
